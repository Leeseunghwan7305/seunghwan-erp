# 사내 ERP 운영 지식 문서

> **용도:** AI 업무 보조 챗봇(RAG) 인덱싱용 내부 문서
> **기준일:** 2026-09-16
> **범위:** 회사·조직 정보 / 업무 규정·프로세스(SOP) / 용어집·데이터 사전
> **주의:** 재고·주문·정산 등 실시간 수치는 이 문서에 넣지 않는다(과거 값이 되어 혼선). 최신 값은 ERP 조회 도구(get_inventory, get_dashboard 등)로 확인한다.
> **주의:** 재고·주문·정산의 실시간 수치는 ERP 조회 도구(`get_inventory`, `list_orders` 등)를 우선 사용한다. 본 문서는 도구로 답할 수 없는 규정·용어·맥락과 기준일 스냅샷을 제공한다.

## 1. 회사·조직 정보

### 1.1 회사 개요
- **업종:** 생활용품·음료 유통(도소매)
- **핵심 업무 흐름:** 구매(발주) → 입고·재고 → 판매(수주) → 출고 → 정산(전표)
- **창고:** 단일 물류창고 `MAIN` 운영 (품목별 재고는 MAIN 기준 단일 레코드)
- **통화 단위:** 원(KRW), 모든 금액·단가는 정수로 관리

### 1.2 부서 구성
| 부서 | 담당 업무 |
|------|-----------|
| 영업부 | 고객 관리, 수주(판매) 접수, 매출 관리 |
| 물류부 | 재고 관리, 발주·입고, 안전재고 모니터링 |
| 관리부 | 회계·정산, 전표 관리, 경비 처리 |

### 1.3 직원 명단 (기준일 현재)
| 성명 | 부서 | 직급 | 입사일 |
|------|------|------|--------|
| 김영업 | 영업부 | 대리 | 2023-03-02 |
| 이재고 | 물류부 | 사원 | 2024-01-15 |
| 박회계 | 관리부 | 과장 | 2021-07-01 |

## 2. 업무 규정·프로세스 (SOP)

### 2.1 발주(구매) 프로세스
1. **발주 판단** — 현재고가 안전재고 미만이거나 수요 예측상 부족이 예상되면 발주 대상으로 선정한다.
2. **발주서 작성** — 공급처(supplier)를 지정해 발주서를 `draft`(작성) 상태로 생성한다. 품목·수량·매입단가를 입력하면 라인 금액과 합계가 계산된다.
3. **발주 확정** — 발주서를 `confirmed`(확정)로 전환하면 **입고 수량이 해당 품목 재고에 자동 가산**되고, **매입 전표(voucher, 미지급)** 가 자동 생성된다.
4. **입고 완료** — 물리적 입고가 끝나면 `done` 상태로 마감한다.
5. **대금 지급** — 매입 전표 대금을 지급하면 전표의 결제상태를 `paid`로 갱신한다. 미지급 전표 합계가 **미지급금**이다.

### 2.2 수주(판매) 프로세스
1. **수주 접수** — 고객(customer)의 주문을 접수하고 수주서를 `draft` 상태로 생성한다. 품목·수량·판매단가를 입력한다.
2. **수주 확정** — `confirmed`로 전환하면 **출고 수량만큼 재고가 자동 차감**되고, **매출 전표(미수)** 가 자동 생성된다.
3. **출고 완료** — 출고가 끝나면 `done`으로 마감한다.
4. **대금 회수** — 매출 대금이 입금되면 전표를 `paid`로 갱신한다. 미결제 매출 전표 합계가 **미수금**이다.

### 2.3 주문 상태 전이 규칙
- 상태 흐름: **`draft`(작성) → `confirmed`(확정) → `done`(완료)**
- **재고·전표 반영은 오직 `confirmed` 전환 시점에 1회 발생**한다. `draft` 상태는 재고에 영향을 주지 않는다.
- 확정 이후 취소·수정은 재고·전표 정합성을 깨뜨리므로, 별도 반품/조정 절차로 처리한다(본 프로토타입 범위 밖).

### 2.4 안전재고 관리 규칙
- 각 품목은 **안전재고(safety_stock)** 기준을 가진다.
- **현재고 < 안전재고**이면 "안전재고 미달"로 분류하고 발주를 검토한다.
- 권장 발주량은 최소한 `안전재고 − 현재고` 이상으로 하되, 발주 단위(BOX/EA)와 리드타임을 고려한다.

### 2.5 회계·정산 규칙
- 전표(voucher)는 주문 확정 시 자동 생성되며, 유형은 매입(purchase)·매출(sale)로 나뉜다.
- **미수금** = 결제상태가 미결제(unpaid)인 **매출** 전표 금액의 합.
- **미지급금** = 결제상태가 미결제(unpaid)인 **매입** 전표 금액의 합.
- 경비(expense)는 주문과 무관한 지출(임차료·복리후생비 등)로 별도 관리한다.

### 2.6 거래처 운영 규칙
- **공급처(supplier)** 에게는 발주(구매)만, **고객(customer)** 에게는 판매(수주)만 진행한다.
- 거래처는 사업자번호로 식별하며, 신규 등록 시 상호·구분·연락처·사업자번호를 필수로 입력한다.

## 3. 용어집·데이터 사전

### 3.1 핵심 용어
| 용어 | 의미 |
|------|------|
| 발주 | 공급처에 물건을 주문하는 구매 행위 (order_type=purchase) |
| 수주 | 고객으로부터 주문을 받는 판매 행위 (order_type=sale) |
| 전표(voucher) | 매입·매출 시 발생하는 회계 증빙. 결제상태를 가진다 |
| 미수금 | 아직 회수하지 못한 매출 대금 |
| 미지급금 | 아직 지급하지 못한 매입 대금 |
| 안전재고 | 품절을 막기 위해 유지해야 하는 최소 재고 수량 |

### 3.2 테이블 사전
| 테이블 | 설명 | 주요 필드 |
|--------|------|-----------|
| item | 품목(기준정보) | code, name, unit, purchase_price, sale_price, safety_stock |
| stock | 품목별 재고 (품목당 1행, MAIN 창고) | item_id, warehouse, quantity |
| partner | 거래처 | name, kind, phone, biz_no |
| order | 주문(발주/수주) 헤더 | order_type, partner_id, order_date, status, total |
| orderline | 주문 상세 라인 | order_id, item_id, quantity, unit_price, amount |
| voucher | 회계 전표 | voucher_type, order_id, partner_id, amount, payment_status |
| employee | 직원 | name, department, position, hire_date |
| attendance | 근태 | employee_id, work_date, check_in, check_out, work_hours |
| account | 계정과목 | code, name, category, entry_side |
| expense | 경비 지출 | expense_date, account, dept, method, amount |
