1프로토타입의 목적

완제품이 아니라 가설을 검증하기 위한 도구입니다. 실제 ERP 구축은 비용과 시간이 크므로, 그 전에 아래 질문에 대한 답을 저비용으로 확인합니다.

검증하려는 것 (In-Scope)

  • 핵심 업무 흐름(구매→재고→판매→정산)이 실제 현장과 맞는가
  • 주요 화면 구성·용어가 사용자에게 자연스러운가
  • 모듈 간 데이터 연결(재고 자동 반영 등)이 이해되는가
  • 필수 입력 항목이 과하거나 부족하지 않은가

지금은 하지 않는 것 (Out-of-Scope)

  • 실제 DB·서버 연동, 대량 데이터 처리 성능
  • 권한·보안·감사 로그 등 운영 기능
  • 세금계산서 국세청 전송, 실 결제/은행 연동
  • 모바일 앱, 다국어, 정교한 예외 처리
프로토타입은 샘플(시드) 데이터로 시작합니다. FastAPI + PostgreSQL로 실제 저장·조회는 되지만, 데이터 규모·정합성·운영 안정성은 본 개발에서 확보합니다.

2핵심 데이터 흐름

유통/도소매 ERP는 아래 순환 고리로 돌아갑니다. 한 모듈의 행동이 다음 모듈의 데이터를 바꿉니다.

품목 등록기준정보
→
구매(발주)입고
→
재고수량 증가
→
판매(수주)출고
→
재고수량 감소
→
회계/정산매입·매출

※ 인사/근태는 위 거래 흐름과 별개로 조직·직원 기준정보를 제공하며, 담당자 지정·급여 계산에 연결됩니다.

3프로토타입 대상 모듈

Module A

재고 / 품목 관리

  • 품목 등록 (코드, 명, 단위, 매입가/판매가)
  • 입·출고 내역 기록
  • 창고별·품목별 현재 재고 현황
  • 안전재고 미달 알림(표시만)
Module B

구매 / 판매 (주문)

  • 거래처(공급처·고객) 관리
  • 발주서(구매) / 수주서(판매) 작성
  • 주문 상태: 작성 → 확정 → 입/출고 완료
  • 확정 시 재고에 자동 반영(프로토타입 로직)
Module C

회계 / 정산

  • 매입·매출 전표 자동 생성(주문 연동)
  • 거래처별 미수금·미지급금 집계
  • 일자별 매출 요약 대시보드
  • 세금계산서 양식 미리보기(발행은 제외)
Module D

인사 / 근태

  • 직원·조직(부서) 등록
  • 출퇴근/근태 기록
  • 월 근태 집계
  • 급여 항목 기반 급여 미리계산(표시)

6제작 방식 (프로토타입 한정)

프론트엔드

  • Next.js (App Router) + React + TypeScript
  • Tailwind 등 유틸 CSS — 일관된 UI 빠르게
  • 서버 상태: fetch / TanStack Query로 API 호출
  • 화면 렌더링·주문 입력·대시보드 담당

백엔드

  • FastAPI (Python) — REST API 서버
  • Pydantic 스키마로 요청/응답 검증
  • 데이터: PostgreSQL + SQLModel/SQLAlchemy, 마이그레이션은 Alembic
  • 재고 자동 반영·정산 계산 등 비즈니스 로직 담당
구분역할기술
Frontend화면·UX, 사용자 입력Next.js, React, TypeScript, Tailwind
API프론트 ↔ 백엔드 통신REST (JSON) · FastAPI 자동 문서(/docs)
Backend비즈니스 로직·데이터FastAPI, Pydantic, SQLModel, Alembic
DB데이터 저장PostgreSQL 16
인프라로컬 개발·구동Docker Compose (web · api · db 3개 컨테이너)
배포공유·피드백프론트: Vercel · 백엔드+DB: Railway/Render 등

Docker 구성

전체를 docker-compose.yml 하나로 묶어 docker compose up 한 번에 실행합니다. 로컬 환경 편차 없이 누구나 동일하게 구동·피드백할 수 있습니다.

webNext.js :3000
→
apiFastAPI :8000
→
dbPostgreSQL :5432
  • web — Next.js 개발 서버, api로 요청 프록시
  • api — FastAPI(uvicorn), 시작 시 Alembic 마이그레이션 실행
  • db — PostgreSQL, 데이터는 볼륨(volume)에 영속 저장
  • 환경변수는 .env로 관리(DB 접속정보·시드 여부 등)
프로토타입 원칙 — 화면 흐름과 모듈 간 데이터 연동(주문 확정 → 재고·정산 자동 반영) 검증이 최우선입니다. FastAPI + PostgreSQL로 실제 API·DB를 두고 Docker로 묶되, 인증·권한·성능 최적화는 본 개발로 미룹니다. "진짜처럼 도는 흐름" > "완벽한 기능".

7진행 일정 (예시, 2~3주)

Week 1
기준정보 + 재고
품목·거래처 등록, 재고 현황, 대시보드 골격 (P1 일부)
Week 2
주문 흐름 연결
발주/수주 작성 → 재고 자동 반영, 매입·매출 정산 (P1 완성 + P2)
Week 3
인사/근태 + 다듬기
직원·근태 화면, 세금계산서 미리보기, 피드백 반영·데모 준비 (P2·P3)

8성공 기준 & 다음 단계

프로토타입이 성공했다고 볼 조건

  • 사용자가 발주→입고→수주→출고를 클릭만으로 끝까지 시연 가능
  • 주문 확정 시 재고·정산 수치가 자동으로 맞게 변함
  • 현장 담당자가 화면·용어에 대해 "이해된다"고 확인
  • 본 개발에 필요한 요구사항·수정점 목록이 도출됨
다음 단계 → 프로토타입 피드백을 반영해 정식 요구사항 정의서(SRS)와 DB 설계를 확정하고, 실제 백엔드·인증·권한을 포함한 본 개발에 착수합니다.
